# Project124

ZX Spectrum Pentagon 1024 project with a host Z80 and a NeoGS Z80 firmware core.

## Build

Run `build.bat` from the repository root on Windows. The build uses the
project's `tools/sjasmplus.exe`.

1. `neogs_sub/build_firmware.asm` builds the firmware and bootstrap, then
   packages them into `neoprog.bin` as
   `[WORD bootstrap_length][bootstrap][firmware]`.
2. `zx_main/main.asm` builds the host image and exports
   `proj124.C`, `boot.B`, `neoprog.C`, and `x86task.C`.
3. The complete NeoGS package is staged in RAM bank 1 only as a `SAVETRD`
   source block. It is **not** included in the resident `proj124.C` image.

## Runtime loading model

- `proj124.C` contains only the resident host Z80 program; no NeoGS bootstrap
  or firmware bytes are embedded in it.
- At startup, the existing Stage 2 routine `load_neogs_firmware_file` searches
  for `neoprog.C`, reads its TR-DOS sectors once into host RAM at `#C000`,
  and records the exact package length.
- The existing GS105a handshake streams the bootstrap section to NeoGS RAM
  `#4000`, starts it, then streams the firmware section to NeoGS RAM `#0000`.
  Both sections come from that one already-loaded file; no second file loader
  or second TR-DOS read is introduced.
- The host proceeds only after the custom firmware returns its ready ACK.
- Stage 5's separate x86 diagnostic fixture is now `x86task.C`.

## NeoGS-to-host debug channel

The custom firmware sends its first text message immediately after startup:
`[NEOGS] STARTUP OK: LOADED FIRMWARE EXECUTION STARTED.`
The host receives this NUL-terminated message before accepting the firmware-ready
`#A2` ACK and mirrors each character to the Unreal Speccy debug port `#EF`.

During operation, NeoGS writes diagnostic text into its own 255-byte queue.
The host requests `CMD_DEBUG_DRAIN` over the command channel; NeoGS returns a
length byte followed by the queued characters over the reverse GSDAT/DBIT
stream. The host forwards those characters to `#EF`. The queue is drained
after x86 execution and memory-test commands. Queue overflow currently drops
new characters until the next drain; it does not block the NeoGS CPU.

Current firmware-originated runtime messages include x86 payload start,
HLT completion, unsupported opcode / IP-boundary errors, and memory-test
start / pass / fail. These are genuine messages generated by the NeoGS CPU,
not host-side status strings.

## Firmware and memory diagnostics

The boot-time NeoGS diagnostic stage resets the private command protocol and
runs the physical-memory/addressing self-test inside the firmware. Its current
test writes and verifies two boundary bytes (offsets `0000` and `3FFF`) on
each of the 64 mapped 16 KiB pages. It verifies page mapping and boundary-byte
retention; it is **not** a full byte-by-byte RAM test.

The Stage 2B firmware self-test executes guest programs for 16-bit
ADD/ADC/SUB/SBB/CMP, 8-bit ADD/ADC/SUB/SBB/CMP, and 8/16-bit
AND/OR/XOR/TEST. The host reports PASS only after the firmware has checked
the resulting registers and FLAGS.

## Stage 5 x86 task file

The host searches the selected TR-DOS `.C` file, validates its descriptor,
reads the sectors into `#C000`, transfers the exact byte length through the
NeoGS DMA window, executes the task, and checks the returned result frame.
The current `x86task.C` fixture is a six-byte diagnostic program
(`MOV AX,BBAA / INC AX / NOP / HLT`), not a full x86 operating system.

### X86T container format, version 1

All multi-byte values are little-endian.

| Field | Size | Meaning |
|---|---:|---|
| Magic | 4 | ASCII `X86T` |
| Version | 1 | Currently 1 |
| Record count | 1 | Number of test records |
| Test ID | 2 | Stable test identifier |
| Expected status | 1 | Expected NeoGS x86 exit status |
| Expected AX | 2 | Expected AX after execution |
| Code length | 2 | Number of x86 machine-code bytes |
| Code | variable | Flat x86 instruction stream |

Each test record repeats from Test ID through Code. The host validates the
container header, record lengths, and file bounds before DMA. It sends only
the machine-code portion of each record to NeoGS. This keeps test metadata
outside the x86 address space and allows multiple independent test records
in one source-generated container.

The host reports the test ID, expected status and AX, actual status and AX,
and the x86 instruction pointer returned by NeoGS. A test passes only when
both expected status and AX match. The suite continues after a test mismatch
and prints aggregate pass/fail counts; a transport or malformed-container
error aborts the suite.

### Structured NeoGS result frame

`CMD_GET_STATUS` now returns six bytes:

1. `A5` result signature
2. x86 exit status
3. AX low byte
4. AX high byte
5. x86 IP low byte
6. x86 IP high byte

The IP is the NeoGS logical x86 execution address at which the interpreter
stopped. For the current DMA layout, the first instruction is at `#5002`.
The host prints this address with each test report.

### Current scope and planned module boundaries

The external pipeline is deliberately independent from the CPU implementation.
The current test fixture uses only the implemented baseline instructions
(`MOV AX,imm16`, `INC AX`, `NOP`, `HLT`). Adding an instruction to the
interpreter must be accompanied by one or more external test records; the
test source and expected results do not need to know how the instruction is
implemented internally.

The next emulator-core modules are intended to be separated as follows:

- `x86_cpu_state.asm` — general registers, segment registers, IP, FLAGS,
  execution state and reset logic.
- `x86_decode.asm` — opcode/prefix decoding and instruction-length handling.
- `x86_exec_*.asm` — instruction-family handlers (data movement, arithmetic,
  logic, control transfer, stack, string and I/O instructions).
- `x86_memory.asm` — physical memory and segmented-address translation.
- `x86_interrupts.asm` — interrupt vectors, interrupt entry/return and flags.
- `x86_runtime.asm` — execution budget, HLT/stop conditions, fault reporting
  and the host/NeoGS service boundary.
- `x86_test_runner.asm` — NeoGS-side test execution support as the protocol
  evolves; host-side file loading and reporting remain in `zx_main`.

The implementation is incremental. The pipeline and result protocol are
being established first; this does not yet mean that the full 8086 instruction
set, FLAGS semantics, stack, interrupts, or complete 1 MiB memory behavior
have been implemented.
