# Project124 — рабочий сценарий и журнал реализации

Обновлено: 2026-11-01

## Цель текущего этапа

Надёжная загрузка отдельного файла `neoprog.C` из TR-DOS в NeoGS через GS105a ROM loader. Формат пакета:

`[WORD bootstrap_length, little-endian][bootstrap][NeoGS firmware]`

Хост Z80 не размещает весь пакет в памяти Spectrum. Он читает первый сектор в `#C000`, передаёт bootstrap и затем повторно использует тот же 256-байтовый буфер для последующих секторов.

## Архитектурные ограничения

- `proj124.C` — резидентный хост Z80/TR-DOS.
- `neoprog.C` — отдельная прошивка NeoGS (bootstrap + custom firmware), НЕ x86-тест.
- `x86task.C` — отдельный файл тестовой x86-программы.
- `neogs_code.bin` собирается из `neogs_sub`; пакет собирается скриптом `pack_neogs.ps1`.
- TR-DOS получает один логический `neoprog.C`, собираемый из 16-КБ частей через отдельные RAM-страницы.
- Буфер чтения хоста: `#C000..#C0FF`, 256 байт.
- Стек приложения хоста: `#AFFF`; буфер TR-DOS не должен использоваться как стек.
- Максимальный размер одного TR-DOS файла: 255 секторов = `#FF00` байт.
- Bootstrap вместе с двухбайтовым заголовком должен помещаться в первый сектор: максимум 254 байта.
- Успех загрузки подтверждается ACK реально исполняющейся прошивки NeoGS. Одного сообщения хоста недостаточно.

## Обязательные критерии завершения потоковой загрузки

1. `build.bat` завершается без ошибок.
2. На TR-DOS создаётся ровно один логический `neoprog.C`, а не несколько одноимённых файлов.
3. Размер файла и число секторов в каталоге соответствуют размеру пакета.
4. Части пакета экспортированы по порядку, без пропусков и повторов.
5. Runtime подтверждает чтение второго и последующих секторов в `#C000`.
6. Передача проходит границы 256 байт, 16 КБ и 32 КБ; отдельно проверить пакет не менее 48 КБ.
7. Последний неполный сектор не приводит к отправке padding.
8. NeoGS возвращает #A1, #A3 и #A2 в соответствующих фазах.
9. Счётчик подтверждённых байтов совпадает с ожидаемым значением.
10. Только после полного лога фиксировать PASS.

### 2026-11-01 — полный runtime PASS после переноса Z80 stack и установки MEM-маркеров (22:59:21–22:59:27)

- IPC-02 PASS: все пять interpreter edge cases прошли; DMA/IPC стабилен.
- MEM-01 PASS: получен completion и result frame `status/AX=0000 0001`; подтверждены 64 страницы RAM, word access и segment/offset wrap. Это первый runtime-проход MEM после переноса Z80 SP из remappable WIN3 в фиксированный WIN0 (`SP=#3FFE`).
- BIOS Stage 1 PASS: IVT/BDA, 640 KiB и text profile.
- INT Stage 2A PASS: IVT lookup, interrupt stack frame, FLAGS/CS/IP, IF/TF, IRET и баланс SP.
- INT Stage 2B PASS: guest `INT 20h` handler исполнился и вернулся через IRET.
- CPU regression PASS: MOV/INC/DEC и флаги; LOOP/JCXZ/JMP/Jcc; стек и near CALL/RET; 16-битная register и memory arithmetic; 8-битная арифметика; логические операции; ModR/M EA формы, смещения и segment overrides; MOV memory forms.

- Stage 5 PASS по runtime: task file найден, сектора загружены в host RAM `#C000`, NeoGS подтвердил DMA completion, result `Status / AX = 0000 BBAB`.
- Финал: `[HALT] Core task pipeline executed entirely. System suspended.` — текущий pipeline дошёл до штатного завершения и остановился в ожидаемом HALT.

### 2026-11-01 — устранение останова MEM-01 и диагностические метки

- Причина найдена статически: `neogs_sub/main.asm` запускал Z80 со `SP=$FFFE` (WIN3), тогда как `x86_mem_map_addr` меняет физическую страницу WIN3 командой `MPAGEX`. Уже первый доступ x86 RAM менял страницу под активным стеком; дальнейшие `CALL`/`RET` могли читать/писать не тот стек и срывать команду `CMD_MEM_TEST`.
- Перенесён стек NeoGS Z80 в фиксированное окно WIN0: `SP=$3FFE`. Код firmware должен оставаться ниже `$3400`; в `build_firmware.asm` добавлен ASSERT на границу `$3400`, чтобы зарезервировать `$0C00` под стек.
- Уточнены комментарии в `x86_memory.asm`: во время x86 RAM теста SP обязан находиться вне `$C000-$FFFF`.
- Добавлены host-маркеры: отправка `CMD_MEM_TEST`, подтверждение завершения команды, получение result frame, вывод `status/AX`, отдельные сообщения тайм-аута ожидания CBIT и тайм-аута result frame. Transport fail MEM больше не маскируется общим IPC edge fail.
- Это исправление обосновано конфликтом адресного окна и стека, но сборка SjASMPlus и runtime ещё не выполнялись. MEM-01 не объявлен PASS.

### 2026-11-01 — повторный runtime-запуск и аудит RETF

- Новый лог: `PACKAGE LENGTH=#347B` (13 435 байт), `PACKAGE SECTORS=#0035` (53 сектора), `STREAM ACK=#347F` (13 439 байт).
- `#347B = 52×256 + 123`: последний сектор содержит 123 байта пакета. `#347F - #347B = 4`; контрольный счётчик соответствует ожидаемой формуле.
- Повторно прошли IPC-01 (`AX=#BBAB`) и IPC-02 (пять edge cases). Лог снова обрывается на старте MEM-01; RAM/segment addressing не подтверждён.
- Статический аудит `x86_real_stack_pop` выявил дефект в RETF: функция сохраняет извлечённое слово в `x86_real_stack_value`, но возвращает в HL уже увеличенный SP. RETF ошибочно использовал HL как popped IP/CS. Исправлено чтение обоих слов из `x86_real_stack_value`; rollback SP при ошибке второго чтения сохранён.
- Исправление RETF ещё не собрано SjASMPlus и не проверено на NeoGS runtime. CPU-02 остаётся ожидающим проверки.

### 2026-11-01 — runtime-проверка загрузки `neoprog.C`

- Лог: `PACKAGE LENGTH = #33BC` (13 244 байта), `PACKAGE SECTORS = #0034` (52 сектора), `STREAM ACK = #33C0` (13 248 подтверждённых GS data bytes).
- `ceil(#33BC / 256) = #0034`; остаток последнего сектора — 188 байт. Счётчик GS соответствует `package_length + 4`, то есть `bootstrap_length + firmware_length + 6`; загрузчик перешёл к Stage 2.
- После Stage 2 отрисована GUI; IPC-01 (`AX=#BBAB`) и IPC-02 (пять edge cases) повторно прошли.
- Пакет меньше 16 КБ: границы 16/32 КБ и стресс-тест ≥48 КБ не проверены. Счётчик байтов не является CRC/проверкой содержимого.
- MEM-01 по-прежнему без результата: лог обрывается на строке старта memory test.

### 2026-11-01 — адаптация CALL/RET из папки 111

- Повторно проверен реальный исполнитель `x86_real_mode.asm`: INC/DEC r16 с сохранением CF, все 16 коротких Jcc, LOOP/LOOPZ/LOOPNZ/JCXZ, JMP rel8, PUSH/POP r16 уже реализованы в активном CS:IP ядре; эти блоки не переносились повторно из `111`.
- Из `111/x86_stack.asm` взят алгоритмический ориентир для near CALL/RET. Реализация адаптирована к штатным `x86_real_stack_push/pop` и проверяемому физическому backend SS:SP; несовместимый стековый код из `111` напрямую не подключался.
- Добавлены опкоды `E8` (near CALL rel16) и `C3` (near RET), с сохранением адреса возврата после imm16 и обработкой ошибок через существующий стековый backend.
- В гостевой регрессионный образ добавлен CALL -> подпрограмма MOV SI,8001 -> RET (без изменения FLAGS), проверка ожидаемого SI изменена на `8001h`; сообщение PASS теперь явно включает near CALL/RET.
- Сборка и выполнение пока не подтверждены; CPU-01 остаётся ожидающим runtime-проверки.

### 2026-11-01 — аудит main и укрепление загрузчика

- Подтверждены в исходниках 256-байтовый буфер `#C000`, чтение следующих секторов по требованию, потоковая отправка firmware и ограничение отправки фактической длиной firmware.
- Подтверждён механизм экспорта единого файла через последовательные `SAVETRD` с append-префиксом `&`.
- Исправлена проверка размера bootstrap в упаковщике: максимум теперь 254 байта, что соответствует формату первого сектора и ASSERT в `neogs_sub/build_firmware.asm`.
- Добавлена проверка счётчика подтверждённых GS data bytes. Ожидаемое значение: `bootstrap_length + firmware_length + 6`.
- Добавлен вывод в runtime-лог фактической длины пакета, числа TR-DOS секторов и числа подтверждённых GS data bytes.
- Предоставленный runtime-лог подтверждает RTC, чтение первого сектора, запуск bootstrap, GUI, базовую DMA/IPC проверку и пять тестов интерпретатора. RAM-тест ещё не подтверждён: полученная запись обрывается на его старте.

## Следующий этап

1. Провести стресс-тест потоковой загрузки пакета размером не менее 48 КБ: пересечение границ 16/32 КБ, повторное использование буфера `#C000` и неполный последний сектор.

4. Продолжать расширение x86/BIOS regression после фиксации результатов текущего полного runtime-прохода.

Сборка и запуск на целевой системе подтверждены предоставленным runtime-логом для текущего набора тестов. Стресс-тест ≥48 КБ и отдельная трассировка far CS:IP остаются открытыми задачами.
