# Project124 — рабочий сценарий и журнал реализации

Обновлено: 2026-11-01

## Цель текущего этапа

Надёжная загрузка отдельного файла `neoprog.C` из TR-DOS в NeoGS через GS105a ROM loader. Формат пакета:

`[WORD bootstrap_length, little-endian][bootstrap][NeoGS firmware]`

Хост Z80 не размещает весь пакет в памяти Spectrum. Он читает первый сектор в `#C000`, передаёт bootstrap и затем повторно использует тот же 256-байтовый буфер для последующих секторов.

## Архитектурные ограничения

- `proj124.C` — резидентный хост Z80/TR-DOS.
- `neoprog.C` — отдельная прошивка NeoGS (bootstrap + custom firmware), НЕ x86-тест.
- `x86task.C` — отдельный файл тестовой x86-программы.
- `neogs_code.bin` собирается из `neogs_sub`; пакет собирается скриптом `pack_neogs.ps1`.
- TR-DOS получает один логический `neoprog.C`, собираемый из 16-КБ частей через отдельные RAM-страницы.
- Буфер чтения хоста: `#C000..#C0FF`, 256 байт.
- Стек приложения хоста: `#AFFF`; буфер TR-DOS не должен использоваться как стек.
- Максимальный размер одного TR-DOS файла: 255 секторов = `#FF00` байт.
- Bootstrap вместе с двухбайтовым заголовком должен помещаться в первый сектор: максимум 254 байта.
- Успех загрузки подтверждается ACK реально исполняющейся прошивки NeoGS. Одного сообщения хоста недостаточно.

## Обязательные критерии завершения потоковой загрузки

1. `build.bat` завершается без ошибок.
2. На TR-DOS создаётся ровно один логический `neoprog.C`, а не несколько одноимённых файлов.
3. Размер файла и число секторов в каталоге соответствуют размеру пакета.
4. Части пакета экспортированы по порядку, без пропусков и повторов.
5. Runtime подтверждает чтение второго и последующих секторов в `#C000`.
6. Передача проходит границы 256 байт, 16 КБ и 32 КБ; отдельно проверить пакет не менее 48 КБ.
7. Последний неполный сектор не приводит к отправке padding.
8. NeoGS возвращает #A1, #A3 и #A2 в соответствующих фазах.
9. Счётчик подтверждённых байтов совпадает с ожидаемым значением.
10. Только после полного лога фиксировать PASS.

### 2026-11-01 — архитектурное решение: размещение x86 BIOS ROM

- По согласованию с пользователем BIOS выделяется как самостоятельный бинарный образ `bios.bin`, отдельно собираемый и сопровождаемый; он не включается в `neogs_code.bin` как Z80-код и не занимает место в 48-КБ адресном пространстве прошивки NeoGS.
- Логический диапазон BIOS гостевого 8086: `F0000h-FFFFFh` (64 КиБ). В текущей схеме `x86_memory.asm` физическая память x86 `00000h-FFFFFh` отображается на 64 страницы NeoGS, начиная с физической страницы 4. Поэтому диапазону BIOS соответствуют страницы NeoGS 64-67 (четыре страницы по 16 КиБ).
- Существующая карта `bios_core.asm` уже резервирует `F0000h-FFFFFh` под P124 BIOS ROM, но явно отмечает, что область пока не read-only. Исполняемого x86 BIOS ROM binary в проекте пока нет: текущие `bios_core.asm` и `bios_video.asm` реализуют Z80-side POST/службы и тестовые BIOS traps, а не полноценный 64-КБ ROM-код 8086.
- Целевой механизм: отдельная сборка `bios.bin` с проверкой размера <= 64 КиБ; загрузка образа в гостевые физические страницы 64-67; чтение по обычному x86 memory backend; блокировка записи в ROM-диапазон при сохранении записи в RAM/прочие области. Вектор сброса 8086 должен вести на физический адрес `FFFF0h` (начальная пара CS:IP = `FFFF:0000`), а ROM должен содержать корректный reset entry.
- Важно: соответствие страниц 64-67 вычислено из текущей формулы отображения памяти; фактическая загрузка BIOS в эти страницы, read-only enforcement и запуск с reset vector ещё не реализованы и не проверены runtime.
- Решение зафиксировано как архитектурное; никаких исходников BIOS или memory backend этим пунктом не изменено.

## Следующий этап — развитие 8086 для XT BIOS

1. **CPU-I/O-02 — сборка и runtime-регрессия:** собрать SjASMPlus, проверить ASSERT #3800 и размер прошивки, затем запустить команду `RUN_X86_REAL`; ожидать прохождение четырёх IN/OUT сценариев и проверки FLAGS/DX. До этого исходники CPU-I/O-01 не считать runtime PASS.
2. **CPU-STR-01 — строковые инструкции:** MOVS/LODS/STOS/CMPS/SCAS без REP, затем отдельный REP/REPE/REPNE с CX, ZF, DF и step limit.
3. **CPU-ARITH-01:** immediate ALU и группы F6/F7.
4. **CPU-SHIFT-01:** shifts/rotates.
5. **CPU-FLAGS-01:** POPF, LAHF/SAHF, CLC/STC/CMC/CLD/STD/CLI/STI и INTO.
6. **BIOS-IO-01:** моделировать MDA/CGA, PIT/PIC, PPI/keyboard и FDC по фактическим обращениям BIOS.
7. После CPU opcode/device coverage вернуться к BIOS ROM write-protect: единая точка `x86_mem_write8`, проверки byte/word и границ `FDFFF/FE000/FFFFF`.
8. **BIOS-02 — формат и сборка ROM:** подготовить отдельный образ существующего XT BIOS размером 8192 байта; проверить checksum/signature и воспроизводимую сборку. Не расширять его искусственно до 64 КиБ.
9. **BIOS-03 — загрузка образа:** загрузить 8192 байта BIOS в верхнюю половину NeoGS page 67, соответствующую гостевому диапазону `FE000h-FFFFFh`; не смешивать образ с `neoprog.C` и Z80 firmware.
10. **BIOS-04 — reset vector:** реализовать старт гостевого 8086 с CS:IP=`FFFF:0000`, проверить чтение opcode по физическому адресу `FFFF0h` и переход из reset stub.
11. **BIOS-05 — тест ROM:** guest regression на чтение нескольких адресов BIOS, запрет записи, сохранность содержимого и доступность соседней RAM. Runtime PASS фиксировать только по полному логу.
12. После BIOS memory path вернуться к CPU-05 (immediate ALU). Текущий лимит resident firmware расширен до `#3800`; дальнейший рост требует контроля размера и stack reserve, а при исчерпании — отдельного решения по размещению/банкингу без удаления регрессий.
13. Отдельно спроектировать расширенный banked firmware layout. Наличие гостевого BIOS в памяти 8086 не увеличивает автоматически размер исполняемой Z80 firmware и не снимает текущий лимит `#3800`.

## Отложенные задачи — вернуться позже

- **FW-09:** стресс-тест потоковой загрузки пакета ≥48 КБ с пересечением границ 16/32 КБ, повторным использованием буфера `#C000` и проверкой последнего неполного сектора.
- **FW-10:** контроль побайтной целостности пакета (CRC/контрольная сумма); STREAM ACK сам по себе проверяет только число переданных байтов.

Эти две задачи остаются отложенными по решению пользователя. CPU-03 из списка отложенных исключён и возвращён в активную работу.

Сборка и запуск текущего pipeline подтверждены предоставленным runtime-логом.
